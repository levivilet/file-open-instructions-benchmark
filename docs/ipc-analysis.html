LVCE file-open message analysis

Return to the measured report

Diagnostic observations on official v0.123.13 (504b29c is the subsequent optimization merge; baseline application commit 75f60f5), using a private Linux AMD64 Xvfb/D-Bus session and isolated application/Chromium state. These message and JSON-representation byte counts are not retired-instruction measurements or structured-clone wire sizes.

One normal open

native File > Open File → renderer-worker → main-area-worker
  main-area-worker → renderer-worker: file size, module selection, create editor
  renderer-worker → file-system-worker → file-system-process: file size/read
  shared-process: launches utility process and transfers the direct file-system port
  renderer-worker ↔ shared-process: file metadata, native dialog, platform paths
  editor-worker ↔ measurement/syntax/extension workers: preferences, text, language, providers
  renderer-worker ↔ editor-worker: create/load/diff/render/focus
  renderer-worker → renderer-process: apply view/DOM/focus commands

Shared-process participates in connection setup; it does not forward every normal content read after the file-system-worker/utility-process port is transferred. Its separate metadata commands remain in the observed file-cache path.

Selected redundant request

GetExtensionViews fetched both Extensions.getViews and the entire extension inventory. All seven built-in views already supplied their CSS, so mergeCss ignored the inventory. Removing that request in this case also removes a disabled-extension path lookup/existence check and a workspace-path query. Views with missing CSS still use the manifest fallback, including application routing. There is no new result cache.

Method and limitations

Start an otherwise identical fresh-profile package with --trace-ipc=* for the existing parent-worker traces. Those proxies miss some direct editor/renderer and file-system-process ports. For wider diagnostic coverage, observe MessagePort postMessage/onmessage/start in the copied package's browser bundles and the actual utility-process HandleElectronMessagePort handler. Preserve original payload delivery and port identity, assign per-endpoint port IDs, record direction/time/request IDs, and collect buffers through CDP. The paired captures use the matched MainArea.openUri request/response span; clipboard verification waits until after opening finishes. Each captured package endpoint reported zero dropped records and zero serialization errors.

Cache and isolated Git extension-worker bundles were outside the package probe; the existing parent proxy trace supplements those boundaries. Shared-process interface calls are observed from the frontend port, and file-system utility traffic at the direct utility port. Node-internal control channels are not exhaustively captured. A full archive and reproduction scripts are retained with the task evidence.

Existing trace proxies add serialization, an extra forwarding hop, batching and trace-file writes. Passive probes still copy/serialize payloads, and the utility probe writes synchronously; CDP also changes execution. Therefore timings from these runs cannot establish speed or instruction cost. The linked controlled comparison instead uses two checksum-verified official v0.123.13 packages, changes only the recorded renderer-worker function, and contains no tracing/probes. Every one of forty alternating-order pairs retains the normal native-open protocol, exact-content/counter/cutoff checks and fresh profiles. The official-release comparison separately validates shipped packages, and independent runs must be inspected without pooling.
